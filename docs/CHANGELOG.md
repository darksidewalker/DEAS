# Changelog

## 0.3.50

- **Unknown wildcard names stop the run.** A `__name__` no imported pack provides is reported and blocks **Run** instead of being sent to the model as literal text.
- **A run records the wildcard seed.** The seed that expanded the imported lists and `{a|b}` choices is submitted with the job, so the recorded prompt can be reproduced exactly and re-used later.
- **Choosing a wildcard folder again replaces it.** Re-importing a folder whose name is already imported replaces that pack, so a moved or copied folder can be added again; another folder may still not take a list a different pack owns.
- **Movie Maker says why a step did not start.** When the plan changed while a shot, chain, music, join or mix step was being prepared, the refusal is shown and recorded in the central Logs instead of nothing happening.
- **My wildcards resolves short references inside a folder.** A `__name__` written inside a list uses the top-level list of that name, and otherwise the list of that name in the calling list's folder; a full path always addresses one folder exactly.
- **Studio can import wildcard folders.** My wildcards browses nested TXT and YAML lists, inserts `__name__` tokens, and previews the expanded prompt. Imports support up to 64 MiB of source files per folder and combine lists that share a name within the folder.
- **My wildcards supports Random and Fixed seeds.** Studio expands `{one|two|three}` choices in positive and negative image and video prompts without a wildcard pack.
- **The Windows folder picker preserves the working directory.** You can move a wildcard folder after import and keep using the saved lists.

## 0.3.49 (untagged; shipped in 0.3.50)

- **Movie Maker keeps the shots it already made.** A shot, chain, music bed, film stitch or mix that finished late — after you edited a scene, removed and re-added one, changed a transition, picked another music track, or switched to another movie — no longer marks the newer plan complete. Each run is bound to the draft, scene revision and effective inputs it was started with, and a reply that no longer matches is dropped instead of written into the film. The shot, chain and music buttons now share one active slot, so a second hand-over cannot replace a running generation; **New** and **Saved movies → open** wait until the running stage settles, and the film panel keeps its **Stop** button while a stitch runs.
- **Stop after this step stops the run.** Pressing it during the last scene (or during a chain that finishes it) no longer starts an automatic film stitch, music generation or mix; a whole Continuity chain still finishes and keeps its clips. The automatic re-stitch now happens only for an intentional single remake or a changed transition.
- **A chain that cannot continue says why.** If Generate cannot start a shot, or cannot pin the previous take's clip after a shot succeeded, Movie Maker now learns that the chain ended: the reason is shown, the clips that were made stay, and the run settles instead of hanging. Stopping a chain in Generate delivers the shot that was still finishing first, then reports the chain as ended once.

## 0.3.48

- **Movie Maker: remove a scene with the ✕ on its card.** The **−** button beside **+** (which removed whichever scene was open) is gone. Every scene card now has its own **✕**. A scene that is not made is removed at once, a made scene asks first (its clip file stays on disk), and a scene that is being made cannot be removed.

## 0.3.47 (untagged; shipped in 0.3.48)

- **Movie Maker: see the whole plan before you apply it.** *Suggest the plan* and *Write my scenes* used to show only counts (new / changed / removed). The proposal now lists every scene as the film would have it: its status (new, changed, unchanged, or made and kept), title, length and what MiniMax H3 will really make, the transition, what happens, the start and end state, the spoken lines with delivery and the media placed in it. A changed scene shows what it was, and scenes that would be removed or kept are named. The story bible is shown open, and so are the suggested music style, tempo and lyrics.
- **Movie Maker: generation settings beside the aspect ratio.** Step 1 now has **Settings** next to the aspect ratio. *This movie's settings* (the default) offers Generate's resolution choices (Native, 480p, 720p, … MP), Steps and CFG. Every shot is handed to Generate with the exact canvas Generate computes for that choice, shown as e.g. *1152×672*, and with explicit Steps, CFG, sampler and scheduler. Before, the size was always the model's default pixel count, and Steps/CFG were whatever Generate last had for the model. *Generate's settings* keeps Generate's own resolution and sampling for the model, and only the aspect ratio comes from the movie. Nothing has to be set in Generate first.
- **Movie Maker: the right Steps and CFG for distilled and base models.** The starting values follow the model: the MiniMax H3 base model starts at 30 steps and CFG 3, while a file named *turbo* or *lightning* is taken as a merge of the 8-step turbo LoRA and starts at 8 steps and CFG 1. That turbo rule reads only the file name; DEAS does not inspect the weights to confirm it (new `variants` family data). The movie's Steps/CFG belong to its default model, which is now saved with the movie. A scene with its own model uses that model's starting values, and it can set its own Steps and CFG in its *Model and LoRAs* block. The music bed is handed over with its ACE-Step variant's own sampling (Turbo 8/1, Base/SFT 50 steps).
- **Movie Maker: music you can steer.** The music now has its own block in step 1 instead of a text box hidden in the music card. It has **12 instrumental presets** (cinematic orchestral, epic trailer, action, suspense, horror, ambient, gentle piano, acoustic folk, bright and upbeat, lo-fi, synthwave, noir jazz). They are data in `src/wizards/musicPresets.json`, so more can be added. Each preset is written twice: as ACE-Step tags and as a YuE2 *Instrumental …, no vocals* Style line. The one matching the chosen music model is used, together with the preset's tempo. There are also a style text, **lyrics** (empty = instrumental), a tempo (BPM) and a lyrics language for ACE-Step 1.5, and *Let the planner write lyrics*. **Write the music with the planner** asks the chosen language model for style, tempo and, if asked for, lyrics from the story and scenes. You see the suggestion first, and only empty fields are filled unless you tick *Replace*. *Suggest the plan* also fills tempo and lyrics where you left them empty.
- **Movie Maker: your work is no longer lost when you switch away (bug).** Opening Replace (or any other wizard) unmounted Movie Maker and threw away the unsaved movie, and nothing survived a restart. Movie Maker now stays mounted once opened, and the movie being edited is kept as a working draft that is restored when you come back or restart the app (*Your unsaved movie was restored*). **New** clears it; saved movie files are still only written by *Save movie*.
- Developer: the manifest gains `render` (source, default model, resolution, Steps, CFG), segment `sampling` and music `lyrics`/`bpm`/`language`/`preset`/`vocals`, validated in TypeScript and `movie_store.rs`; `WizardHandoff` gains `sampling`, `resolution`, any `aspect` and music `bpm`/`language`, applied by Generate in Advanced and Beginner.

Changing cut ↔ blend only re-stitches the film.
- **Movie Maker: the plan sets up the music; no lock switch.** *Suggest the plan* also proposes the music style for the whole film (length, model and mix stay the defaults). The *Locked* switches are gone: re-planning leaves made scenes alone unless *Also rewrite made scenes* is ticked in the proposal.

## 0.3.41 (untagged; shipped in 0.3.48)

## 0.3.40 (untagged; shipped in 0.3.48)

- **Movie Maker: the music can go to H3 as an audio reference instead of being mixed in.** The Music step has a new choice, **How the music joins the film**: *Mix it under the finished film (your exact track)* — as before — or *Give it to H3 as an audio reference of each shot*. In the second mode every cut shot is handed to Generate as a REF2VA draft with its cast pictures **and its slice of the track** (starting where the shot sits in the finished film, as long as the shot) as an audio reference; H3 makes its own sound guided by the music — it is not a copy of the track — and no mix is added afterwards: the two ways are never combined, so the music is never doubled, and the mix button says it is off. The slice has to be 2–15 s and the track long enough for the shot's place in the film; the shot needs a cast picture (H3's audio reference needs a picture reference too); chains of continued shots cannot use it (each step would need its own slice) and say so. - Developer: `native_movie_music_info` (the track's length by ffprobe); `tools/movie_gpu_session.py --audio-ref <session>` runs the real-model check of this mode (the GPU was busy with desktop streaming when it was first tried, so it has not run yet); a real run showed that H3 refuses a slice that runs past the end of the track (`audio 1 must be between 2 and 15 seconds (got 1.875)`), which the hand-over now prevents.
## 0.3.39 (untagged; shipped in 0.3.48)

- **Movie Maker: every shot can have its own model and its own LoRAs.** Each shot has a **Model and LoRAs** block: pick another installed MiniMax H3 model than the default for that shot, and add up to 8 LoRAs of that model family with a strength each (−4…4). ## 0.3.38 (untagged; shipped in 0.3.48)

- **Movie Maker: the music bed is levelled before it is mixed.** A real run showed that a generated ACE-Step track is very quiet (about −34 dB RMS), so the default *Music level* (−14 dB) left the bed some 20 dB below the speech — practically inaudible, 26 dB with ducking. The mix now first brings the track to a fixed loudness (EBU R128, −24 LUFS) and then applies your level, so the same setting means the same for a quiet generated track and a loudly mastered song; measured on the same film the bed now sits about 12 dB below the speech and about 17 dB below it while the film speaks (ducked). Level and ducking are still yours to tune by ear.
- Developer: `tools/movie_gpu_session.py` — the Movie Maker GPU acceptance session (first take, continued shot, ACE-Step track, join, real mix with measured ducking) on a throwaway backend; `--precheck` compiles every intent offline, `--remix <session>` re-runs only the mix measurement without the GPU.

## 0.3.36 (untagged; shipped in 0.3.48)

- **Movie Maker: a music bed under the film.** A new **Music** step takes one music file you choose (**Choose a music file**; WAV, MP3, FLAC, OGG, Opus, M4A, AAC, WMA) and mixes it under the joined film. **The film's own sound is kept — including the speech MiniMax H3 generated:** the music is turned down whenever the film itself is loud (**Duck under the film's sound**, 0–30 dB, 0 = off), so speech stays audible; the music's **level** (−40…6 dB) and a **fade-out** at the end (0–10 s) are yours to set. Generating the track with ACE-Step/YuE2 and the optional H3 audio-reference mode are the next steps; speech stays H3's own for now. Six locales, search entries, [the guide](DARK-WIZARDS.md#music-bed).
## 0.3.35 (untagged; shipped in 0.3.48)

- **Movie Maker: continued shots.** A shot marked *Continues the previous shot* is now made together with the first shot of its chain (a cut starts a new chain). The first shot's button becomes **Make the chain (n shots)** / **Prepare the chain in Generate**; Generate runs the chain as H3 Continuity — a first take, then every following shot continues the clip before it with its own action text, in *segment* output mode so each shot's file holds only its new footage — and reports each shot's clip back, so every shot of the chain is recorded (and played) as it finishes. A failing step marks that shot failed and leaves the rest of the chain *not made*. The cast pictures of all shots in a chain are the references of every step. The film join now also takes continued shots (their segment-mode clips are joined in order like any other clip). Rerunning always remakes the whole chain from its first shot. Real footage of continued shots (identity, visual joins, audio) is not yet checked on a real model.
- Developer: the pinned-clip update of the continuity plan is the pure `pinStep`. Extracting the plan runner into a hook turned out to be circular with `run()` (the runner starts steps through `run()`, and `run()` registers the running step), so the chain uses a plan selector instead (`plan = moviePlan ?? userPlan`), which leaves the runner as it is.

## 0.3.23

- **Agent API: scripts and agents can queue generations through a local `/v1` plane ([#53](https://github.com/darksidewalker/DEAS/pull/53), thanks @gogood73).** A new **Backend → Agent API** panel configures a loopback-only HTTP plane (`http://127.0.0.1:<port>`, default port 8790): queue pictures, videos, reference bundles (RefMods) and one-cycle continuity films, read results and files back, and let one agent share the card with the rest of DEAS through a strict VRAM handoff. **It ships switched off**: with no `deas-agent-settings.json` nothing starts, no port is bound, and a fresh install behaves exactly as before. Every request passes three walls in a fixed order — an allowlisted browser `Origin` (an empty allowlist denies all cross-origin), a loopback `Host`, and the standing key when you set one; the bind address is never configurable, only the port. The panel never writes without showing its diff and getting an explicit confirm, and refuses a write while a cycle is live. Operator unload/restore commands and the readiness URL live in `deas-agent-guard.json` and are never shipped in the binary. While a cycle owns the card, DEAS refuses environment update, environment move, app restart, stock memory admissions and stock submits with `CYCLE_FENCE: … waits until it finishes`, and a watchdog ends a run whose card went silent. Global search finds every control under *Agent API*. The usage guide — quickstart, one live-tested JSON per option, shelves and workflows — is [Agent API](AGENT-API.md). Re-verified on Linux at the merge tree (Rust suite, Clippy, type check, core and interface suites, and the plane's smoke test); the author's live GPU battery over four image families and H3 video, and Windows (operator commands run through `cmd /C`), were reported by the author and not repeated here.
- **LoRA families now believe the trainer, not the upload tool.** A LoRA's `modelspec.architecture` is stamped by whoever uploaded the file and is wrong often. Kohya's own `ss_base_model_version` / `ss_network_module` tokens, and a positive tensor-signature match against a family the claimed architecture cannot confirm, now outrank that claim. On the reference library this corrected eight anima LoRAs that had been filed as SD 1.5 (a family whose LoRA signature list is empty can no longer win by claim alone). The model index re-describes every stamped file once after this update, so the first Library scan takes longer than usual.
- **Two deadlocks and one infinite recursion in held Workbench rows are fixed.** Cancelling, reading an audio source, or starting Auto Refine from an id that resolves to the caller's own current row used to lock the same session twice (a frozen DEAS) or recurse forever; such an id is now handled on the session that already holds it, and Auto Refine still refuses a cross-scope source with the known message. Found while bridging the agent plane, fixed on the stock path.
- **Canvas sanity at the native walls: the family grid became the law, not the generic 64.** The native compile floor for width/height is now 8 instead of 64 — the 64 was one family's number wearing a generic costume, while 1×1 is impossible on the 8-aligned latent grid and 56×56 renders on an 8-grid family (a 1×1 direct intent still fails, one latent cell down). What the old 64 caught by accident is now said on purpose: every family's own canvas grid from the family plugin (`multiple`: 8 — sd15, pixart, hunyuan-dit; 16 — anima, moss-image and 21 more; 32 — minimax-h3, ltx-2; 64 — sdxl) must divide every canvas edge, at both the Agent API door and native preparation, for the canvas itself and for a **Hi-Res Regenerate** target, a **Resize input** and an inpaint crop target. A 24×24 picture on anima used to clear the generic wall and be padded inside the model; it is now refused with *anima pictures sit on a 16-pixel canvas grid*. A family that declares no grid (music, SAM) keeps only the generic wall — nothing is invented for it. Studio agrees with the native wall instead of being stricter: its size controls floor is 8, the accepted canvas is a multiple of the chosen model family's grid, and its intent check (`execution`) measures the canvas, a Hi-Res Regenerate target, a **Resize input** and an inpaint crop target against that same family grid. Auto Refine no longer raises a crop target to a hardcoded 64 either — the floor there is one cell of the family grid, so a 16-grid family keeps a legal 32 instead of being moved to 64. Visible consequence: a hand-typed or historical SDXL canvas that is not a 64-multiple (a 1000×1000 square) is now refused instead of quietly padded — pick 960, 1024 or 1088. An image→image run that keeps the input's own size (no **Resize input**, no crop) is also checked against the law before preparing, reading the placed file's PNG/WebP header instead of guessing: an oversized input is refused naming its dimensions, where before the job was queued and the limit was hit later. A truncated PNG header no longer risks a panic in that check.

## 0.3.20

- **H3 latent upscale and Hi-Res Regenerate: correct memory estimate, chosen weight residency.** Every `DaSiWaH3TiledUpscale` and `DaSiWaH3HiResRegenerate` node now gets `tile_memory_estimate`, `weight_residency: "auto"`, `max_resident_gb: 0`, `temporal_join: "prefix"` and `tile_references: "full"`. With DaSiWa node pack 0.5.62, ComfyUI sizes its memory reservation for one tile instead of the whole frame: a 4K window was estimated at about 105 GB, so the whole model was offloaded. Windows were joined by an anchor keyframe and a crossfade; now the previous window's finished frames start the next one frozen (exact, no extra tokens). Older packs ignore these inputs and render as before. **☰ More upscaler options** adds **Temporal join** (Prefix / Crossfade), **Tile references** (Full / crop reference videos / crop videos and pictures), **Weight residency** (Auto / Keep as much as fits / Stream) and **Max resident weights (GB)**; changed values need pack 0.5.62 (greyed with the upgrade hint otherwise, and a direct intent is refused at preparation). Measured on a 16 GB RTX 4070 Ti SUPER (int8 H3, 544×960 → 2176×3840, 124 frames): with **Keep**, resident weights 0/0 → 1.9/8.4 GB per window and peak 9.0 → 11.4 GB at the same refine time (387 → 384 s); with the default **Auto** the estimate is 27.7/26.9 GB instead of 104.7/41.9 GB, nothing is loaded and peak stays 9.0 GB (381 s); see [verification](VERIFICATION.md#h3-low-vram-tiling-node-pack-0562-deas-0320).
- **Chat: Retry.** A **Retry** button under the conversation asks the model again for the last answer when it went wrong, came back empty, broke off or failed with an error. The new answer replaces the old one; the question is not saved twice. Pictures sent with that question are sent again while this session still holds them; otherwise the model is told they are no longer held.
- **A fresh environment installs on Linux Mint, Ubuntu and friends ([#50](https://github.com/darksidewalker/DEAS/issues/50)).** DEAS requires that nothing in its environment is writable by group or other — otherwise another account could swap a Python file the backend executes. But the installer created the folders, the venv and the checkouts with your account's umask, and distributions with user private groups default to `0002`. The install finished and then DEAS refused its own output: "Owned environment must be owned by this user and not group/world writable". DEAS now sets a safe file-creation mask at startup (a stricter umask you chose stays; only the group/other write bits are cleared), writes its own folders and manifests with explicit permissions, and opens an environment installed the old way by clearing those bits itself — **Logs** shows one `backend.owned-environment` line saying how many entries it corrected. The refusal that remains now names the folder, its permissions and the `chmod go-w …` that fixes it, and the Troubleshooting table has the matching entry.

## 0.3.7

- **DEAS updates itself on Windows (#43).** **Upgrade → Everything** used to stop with *self-update is unsupported on this platform (including Windows locked executables)* whenever a newer DEAS existed, and ComfyUI and the node packs were not updated either. Windows cannot overwrite a running `deas.exe`, but it can rename it. DEAS now downloads the release's `deas.exe` beside itself and checks its SHA-256 and that it is a 64-bit Windows program. It renames the running file to `deas.exe.old`, puts the new one in place, verifies it, and asks **Restart DEAS now?** with **Restart now** or **Later** (the new version then starts the next time you open DEAS). `deas.exe.old` is removed on the next start. No admin rights, helper script or registry change.
- **Antivirus and ransomware protection are handled.** Windows Security scans a fresh download and can hold it for a moment, so DEAS waits for the scan (up to 45 s) and re-checks the file before and after the swap. If anything goes wrong, the previous `deas.exe` is put back. A download that Windows Security quarantined or blocked is reported as such, with Protection history as the place to check. Before downloading anything, DEAS checks that it may write to its folder. When **Controlled Folder Access** (ransomware protection) blocks it, the message says so and names *Allow an app through Controlled folder access*, or suggests moving DEAS out of Documents or Desktop.
- **Local GGUF models in Prompt Forge and Chat no longer fail with *Windows Error 0xc000001d*.** The error (*Prompt Forge h3: 422 Could not reach local at : [WinError -1073741795] Windows Error 0xc000001d*) means "illegal instruction". The llama-cpp-python wheels DEAS installed are built upstream on whatever CI machine is available, with that machine's CPU features. Several releases, including the newest one (0.3.37), therefore use AVX-512, which most desktop CPUs lack (Intel 12th–14th gen, AMD before Zen 4). On Linux the same build crashes the process. DEAS now installs a release whose CPU library contains no AVX-512 code (0.3.36 for CPU, CUDA 13 and Vulkan, 0.3.37 for CUDA 12.1 on Linux) and self-tests it after installation, with a Logs warning if the processor still cannot run it. When DEAS starts the backend of an older environment that has such a build on a CPU without AVX-512, Logs say so. **Existing environments: run Upgrade → ComfyUI and node packs (or Everything) once** to replace the installed wheel. The node pack (0.5.60) now names the processor problem instead of *Could not reach local*.
- **Local GGUF runs on the GPU on AMD and on Windows with a GTX 10-series card.** AMD environments used the CPU-only llama-cpp-python, because upstream publishes no ROCm builds. They now get the Vulkan build, which runs on the Radeon through the graphics driver. Windows environments with a Pascal card (GTX 10-series, CUDA 12.1 profile) could not install llama-cpp-python at all: there is no CUDA 12.1 Windows build newer than 0.3.4. They get the Vulkan build too, which uses the NVIDIA driver and needs no matching CUDA runtime. If no Vulkan driver or GPU is found, the install logs a warning and local GGUF runs on the CPU.
- **Everything no longer fails where DEAS cannot replace itself.** AppImage and other unsupported platforms skip the app step, still update ComfyUI and the node packs, and show the newer version with **Open releases page**. **DEAS app only** is greyed out there, with the reason. A failed app update also offers **Open releases page**.

## 0.3.6

- **Face refine and other SAM3 post-processes no longer fail right after a large generation.** ComfyUI keeps the previous run's cached results and model memory until free RAM falls below its own headroom (about 10 % of RAM), so straight after an H3 generation the SAM3 video window could see too little free memory and refuse (*SAM3_VIDEO_WINDOW: estimated incremental host memory … exceeds 75% of available memory*) although ComfyUI would have released that memory on demand. Before refusing, the window now asks ComfyUI to free what it only keeps for speed, in its own order: old cached results first, then model pinned memory, then current cached results (anything dropped is reloaded when needed). It refuses only if the memory is still short afterwards, and Logs show the before/after figures. VRAM was not the cause: SAM3 and H3 load through ComfyUI, which already makes room on the GPU itself. Reaches an existing environment at the next backend start; no node pack update.

## 0.3.5

- **The host memory check no longer blocks jobs by default.** 0.3.4 refused a job when the model files it names plus its decode buffers exceeded free RAM (for example *estimated need 40.1 GiB … 43.1 GiB available*). That estimate counts every model as resident at the same time, which ComfyUI's memory management (offloading, smart memory, unloading one model before the next) does not do, so jobs that run fine were refused. The check is now off unless you opt in: `DEAS_HOST_MEMORY_ADMISSION=warn` writes the estimate to **Logs** and starts the job, `=block` restores the refusal.

## 0.3.4

- **Studio no longer floods a slow backend until it stops answering (#39).** While Studio waited for its first model/node list it re-asked the backend every 3 seconds and threw away every answer that arrived after the next question had been sent. On machines where ComfyUI needs more than 3 seconds for `object_info` (all three reporter logs: 3.8–7 s for a 1.5 MB answer on Windows) no answer was ever accepted, the questions queued up inside ComfyUI faster than it could serve them (each reply took 0.75–3.9 s longer than the one before), and after about two minutes every request — Studio's, the Comfy tab's and a browser's — timed out: *Backend not ready – backend features unavailable* while Backend → Test was green, `/object_info` taking minutes in a browser and the Comfy tab stuck on its logo. Studio's waiting poll now joins the request already in flight instead of replacing it, accepts the answer whenever it arrives, and asks again only after a failure. Opening Options/Post/Dials, Reload and finished downloads still fetch fresh lists.
- **Heavy jobs are checked against free memory before they start.** The reported crash was the operating system killing DEAS and its backend mid-run (recorded peak 48.1 GB); that kill now happens in DEAS first. Before a job starts, DEAS adds up the model files the job will load and the full-frame decode buffers its chosen path needs, compares the total with this machine's free memory, and stops with the numbers in **Logs**: *estimated need 55.9 GiB (42.5 GiB in 6 model files + 13.4 GiB full-frame decode buffers), 3.2 GiB available of 61.7 GiB* — plus what to change: close memory-heavy programs, turn on **Streaming decode** where it is offered, or lower canvas/duration. The job is not consumed, so starting it again after freeing memory just works. The headroom scales with the job, so small jobs still run on a busy desktop, and a job whose models cannot be found is never refused on a guess. `DEAS_HOST_MEMORY_ADMISSION=warn` starts anyway with the same note in Logs; `=off` skips the check. Measured against the real 362-frame H3 Hi-Res 2K case, the estimate is accurate to about 1 GiB.
- **Enhanced video preview keeps moving during long waits.** Each preview clip still plays to its end before a newer one takes over; when no newer clip has arrived, DEAS now holds the last frame for one second and replays the current clip instead of freezing on it. Stages that send no sampling previews (upscaling, face refine, export) therefore no longer look stalled. The finished result replaces the preview as before. (PR #42)
- **LoRA details: own trigger words, own cover and prompt examples.** In Library → **Model details** of a LoRA, **Edit trigger words** takes one word or phrase per line (up to 50; save an empty list to clear them). The local list is kept in the model's `.deas.json` sidecar, survives **Refresh metadata**, and is what Library search and Studio's LoRA details use. **Replace preview…** converts an image from your device to a PNG of at most 1024 px and saves it as `<file>.deas-preview.png`, which takes precedence over the provider thumbnail and existing sibling previews; those files stay untouched and the cover moves/deletes together with the LoRA. **Prompt examples** lists up to six still images of the matched Civitai version with copy buttons for their positive and negative prompts; **Refresh metadata** adds them to entries fetched before this version. Thumbnails load from Civitai only while the details are open (mature ones stay blurred when blurring is on). New native command `native_model_edit_lora`. (PR #42)
- **Older environments get an Update button instead of a technical error.** An environment installed by an older DEAS whose pinned node packs (ComfyUI-GGUF, -KJNodes, -HyperFlow-Flash, -Dials) are at other revisions was refused at startup with the raw toast *Technical error: ComfyUI-HyperFlow-Flash install does not match its pinned revision; re-provision required*, while the Backend header read *Not installed*. DEAS now shows **Environment needs an update** with an **Update environment** button and the reason under *Technical details*; the header reads **Update required**. After confirmation the same mutation as **Upgrade → ComfyUI and node packs** fetches the pinned revisions; models, inputs, outputs and settings stay unchanged, and the environment opens when it succeeds. Nothing changes before the confirmation. Packs whose files were modified (`source changed`) stay refused. New native command `native_install_repair` (one-time preview token, explicit confirmation).
- **The uv download retries transient failures.** The first-run download of the pinned uv release from GitHub now makes up to three attempts (2 s and 5 s backoff) when a connection drops, times out or the server answers 429/5xx, logging each retry; a missing asset (4xx), an oversized body or a checksum mismatch fails at once. A single network hiccup no longer aborts the installation and pushes the next attempt into `deas-environment-2`.
- **Studio says when the backend knows models the list does not.** Files copied into the models folder by hand reach the backend's lists before DEAS's model index sees them. The Models and LoRAs docks now show a note with the number of such files beside **Reload** (which adds them). DEAS still does not rescan on its own.
- **Triton is installed where the GPU profile supports it.** Windows NVIDIA environments (CUDA 13 profile) now get `triton-windows==3.8.0.post29` right after Torch, under the same Torch constraints; Linux NVIDIA and Linux ROCm keep receiving Triton through their Torch wheels. The final installer check imports `triton` on these profiles and records `tritonVersion` in `deas-install.json`. Existing Windows environments get it through **Upgrade**. Pascal (CUDA 12.1) and CPU environments get none (Triton cannot compile for compute capability 6.x). Studio's **torch.compile** option disables `inductor` with a reason, and native admission refuses such a job, when the running owned GPU environment has no Triton; `native_recipe_prerequisites` reports this as `allowlist.triton` for the owned backend only.
- **No KJNodes triton traceback in Logs.** On systems without `triton` (stock Windows), ComfyUI-KJNodes logged a full traceback on every backend start for its optional *Patch Triton VAE* node. DEAS's ComfyUI log now condenses exactly that block into one `INFO` line; any other error inside or after it is passed through unchanged.
