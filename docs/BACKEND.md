# Installer, backend, folders and language settings

[Documentation index](README.md) · [Plan](PLAN.md)

## Setup path

Setup is one automatic path in the **Backend** tab, which sits in the right-hand utility tab group with Monitoring, Run Plan and Logs; Studio, Library, Prompt Forge, Chat, TVE and Comfy remain on the left. Setup remains accessible after installation; Backend's left menu also holds Startup optimizations, LLM backend and Provider authorization. The install review shows the hardware findings, and a sticky **Review & edit installation** panel on the right holds the storage folder, the Director package (checked by default; Forge · RefMods · Continuity · Output are included parts, not separate choices), a dense plan summary with the step chain, collapsed native warnings and the single green **Start install** authorization. Backend, optional packages, the ComfyUI Git ref and an existing-backend address live under Advanced options. The native plan re-prepares automatically after every edit; any edit invalidates the prepared plan, and choices lock during execution. Managed setup defaults to a new `deas-environment` directly beside the running executable, selects a compatible NVIDIA or AMD (Linux) profile or an explained conservative CPU recommendation, and leaves optional packages/extensions off. The native Linux/Windows x86_64 CPU/NVIDIA baseline installs ComfyUI directly (Windows runtime installation is not yet accepted). Full new CPU and NVIDIA installations, framework computation, owned backend start, real API readiness and stop are verified on Linux. Intel (and AMD on non-Linux systems) and optional Sage/Radial/Flash/FFmpeg currently block execution with named reasons; there is no simulated success. The AMD Linux path installs and verifies through the same plan machinery but awaits acceptance on a real RDNA card (§4.8 caveats).

Shared `NeuralBlob`, `NeuralPath`, `NeuralGraph` and reusable `NeuralIncludedFeatures` components serve both setup and studio features. Historical animated-road settings are not the current setup contract; preserve reduced-motion behavior and avoid continuous repaints. See [primitive ownership and references](NEURAL-PRIMITIVES.md).

## Folder selection and relocation

After successful installation or checked reopening, **Backend → Environment folder** shows the installed DEAS environment’s full path. **Open environment folder** reveals it in the system file manager, even while the backend is stopped. This is the environment root, not the separately configurable models/input/output folders; an uninstalled draft is never shown as an installed environment. Opening it does not start or modify the backend.

**Move environment…** (beside it) moves the whole environment to a new folder inside a chosen parent, keeping the folder name. It requires no running installation, download or Studio job. After confirmation, a running owned backend is stopped gracefully and restarted at the new location; a stopped backend stays stopped. Same drive: one rename. Another drive: a full copy (links kept as links on Linux; on Windows only uv-cache links are dropped, any other link aborts the copy), and the original is removed only after success. DEAS then rewrites every stored absolute path from the old root to the new one: `deas-plan.json`, `deas-install.json`, `deas-settings.json`, `deas-models.yaml`, `venv/pyvenv.cfg`, text scripts in the venv's `bin`/`Scripts`, the Python path in uv's Windows `.exe` launchers, and absolute links into the old root (uv cache). The moved `venv` Python must start from its new prefix and import PyTorch, and the owned-launch identity is captured anew; on failure the rewrite and move are undone. Models, inputs and outputs in your own folders are not touched.

Native folder selection resolves symlink aliases to their real existing directories before planning; installation execution still refuses symlink substitutions. The first installation review offers optional existing models, input and output folders. They remain an in-memory draft until Start install authorizes the immutable plan; no folder settings or data are written by selection alone. After success, those paths are handed directly to Studio; selecting them again in Settings is not required. Studio rescans a changed model root even if an earlier scan is still pending and ignores results/errors from the old root. Choose the models root containing category folders such as `checkpoints`, `diffusion_models` and `loras`, not an individual category folder.

Relocation currently supports Linux; other platforms reject movement without changing files. After installation, the Backend tab separates saving paths from the explicitly selected **Move files & save folders** action. Moving checks all changed trees for conflicting filenames before copying; it never overwrites a destination file. Close other applications using these folders, stop the owned backend and finish downloads first. Copies are verified before settings are switched and originals removed. Errors preserve original data; cleanup warnings identify retained duplicates. Symlinks inside relocated trees and overlapping trees are rejected rather than followed.

## Language plugins

German, English, Turkish, French, Simplified Chinese and Japanese menus/texts live in decentralized module-owned `locales/*.json` files. Data-only manifests under `src/languages/<id>/manifest.json` register bundled UX languages. Switching language preserves IDs and choices; key parity and source-reference checks run in tests. Raw technical logs/errors remain original. See [localization contract](LOCALIZATION.md).

## Native installer coverage

Rust directly implements verified uv bootstrap, managed Python, isolated venv, ComfyUI reference checkout, pinned CPU/NVIDIA/AMD-Linux Torch selection and required runtime checks. Selected DaSiWa capabilities share one nodepack dependency, fetched only when needed; selecting a capability does not yet implement its studio UI or install model weights. Plans fix hardware and framework identities and require separate confirmation. Targets must be absent, with an existing nonsymlink parent. Fresh installs refuse existing targets. Explicit owned-environment Upgrade/Reinstall is separate: review its plan; reinstall can replace the owned venv and is not rollback.

Successful native provisioning or checked reopening authorizes the owned backend. It auto-starts by default after installation/open and on app restart; disable **Auto-start backend** in **Backend** for explicit manual startup. Manual Stop is not automatically undone. Native manifests and launch files are checked before reuse, and an OS-held environment lock prevents another DEAS instance from starting the same environment. Lifecycle commands verify exact child/listener ownership and real bounded ComfyUI API responses, expose status/logs and stop only the owned process group. They do not adopt arbitrary running listeners or imply generation readiness. Linux local-process/HTTP fixtures and full newly installed CPU/NVIDIA ComfyUI stacks are verified, including an 32 GB test GPU CUDA computation and owned service launch.

Read [the port ledger](INSTALLER-INTEGRATION.md) and [native IPC details](../src-tauri/README.md) for unsupported options and verification limits. Node requirements explicitly resolve NVIDIA VFX wheels and select backend-specific llama-cpp-python binary wheels, following the reference installer; unavailable wheels fail without a source build or silent CPU fallback. llama-cpp-python is pinned per wheel family (cpu, cu130 and vulkan 0.3.36; cu121 0.3.37). AMD plans and Windows Pascal (CUDA 12.1) get the Vulkan family. AMD has no ROCm wheels upstream, and cu121 has no Windows wheel newer than 0.3.4. Vulkan runs through the GPU driver; the install self-test logs a warning when no Vulkan driver or GPU is found, and local GGUF then runs on the CPU. At backend start, DEAS logs a warning when the installed llama-cpp-python predates the pin on a CPU without AVX-512, or when it is the wrong build (for example CPU-only on AMD). The pinned releases were picked because their `ggml-cpu` library contains no AVX-512 code. Upstream builds use the CI runner's native CPU flags, and releases that need AVX-512 crash on most desktop CPUs with *Windows Error 0xc000001d* (illegal instruction) or SIGILL. After the node requirements are installed, a self-test runs ggml-cpu's vectorized fp16 conversion; if it fails, Logs get a warning and only local GGUF Prompt Forge and Chat are affected. Complete selected nodepack installation, required Director/Continuity registration and owned API lifecycle are verified on the 32 GB test GPU; model generation and every included feature recipe remain separate acceptance work. Full Go-installer parity is unfinished.

## Environments from an older DEAS version

DEAS pins the revisions of the node packs it installs (ComfyUI-GGUF, ComfyUI-KJNodes, ComfyUI-HyperFlow-Flash, ComfyUI-Dials). When a saved or chosen environment has one of them at another revision, typically because an older DEAS installed it, the environment is not opened as it is. The Backend tab shows **Environment needs an update** with the environment path, the exact reason under *Technical details* and an **Update environment** button; the header reads **Update required** and no new installation is planned automatically. After you confirm, DEAS performs the same mutation as **Upgrade → ComfyUI and node packs**: it fetches the pinned pack revisions and installs their dependencies in the environment's own venv under the recorded Torch profile. Models, inputs, outputs and settings are not touched. When the update succeeds, the environment opens and the backend starts according to **Auto-start backend**. If it fails or is cancelled, the failure is shown in the installation status and the offer reappears for another attempt. Choosing a different folder dismisses the offer. Pack checkouts whose files were modified (`source changed`) are not repairable this way and stay refused.

## Adopting a foreign installation

Under Advanced options, **Adopt a foreign installation (rebuild its venv)** lets DEAS take over a local ComfyUI folder it does not already manage. The folder must contain `ComfyUI/main.py`; symlinks and traversal are rejected, and a folder DEAS already manages is refused (reopen it from the saved environment instead). The plan warns, and an explicit confirmation dialog gates the start: DEAS deletes and rebuilds the folder's venv and runtime, resets the chosen ComfyUI ref and manages the backend from then on. Models, inputs, outputs and untracked files are kept. Running servers are not adopted; connect them through the backend address instead.

## Triton

Triton is the GPU kernel compiler behind Studio's **Torch Compile** option (its default `inductor` backend) and behind Triton-based nodes such as KJNodes' *Patch Triton VAE*. DEAS provides it wherever the GPU profile supports it:

| Environment | Triton | Source |
| --- | --- | --- |
| Linux, NVIDIA (CUDA 13 profile) | `triton 3.8.0` | dependency of the pinned `torch 2.14.1+cu130` wheel |
| Linux, AMD ROCm | `triton 3.8.0+…rocm10.0.0` | dependency of AMD's `torch 2.13.0+rocm10.0.0` wheel (resolution checked; no AMD hardware run yet) |
| Windows, NVIDIA (CUDA 13 profile) | `triton-windows==3.8.0.post29` | extra PyPI wheel installed right after Torch, held by the same Torch constraints |
| Pascal / GTX 10 (CUDA 12.1 profile), CPU | none promised | Triton does not compile for compute capability 6.x; CPU needs no Triton |

On the GPU profiles above the installer's final check imports `triton` and records its version as `tritonVersion` in `deas-install.json`; a failed import fails the installation instead of leaving a silent gap. Windows environments installed before 0.3.4 get `triton-windows` through an explicit **Upgrade** (ComfyUI and node packs); opening or starting an environment never installs it.

For the running owned GPU backend, Studio's **Options → torch.compile** disables `inductor` with a reason when the environment has no usable Triton (Pascal, or a Windows environment not yet upgraded); other compile backends stay selectable. Native admission refuses an `inductor` job for that backend before any upload. External backends and CPU environments are not judged. Whether Torch Compile then runs fast, or at all, on a given model is separate: on Windows, PyTorch's inductor may additionally need the Microsoft C++ build tools for some kernels; this is not verified or provisioned by DEAS.

## Backend lifecycle and startup settings

After successful installation/checked reopening, Backend provides Start/Stop/Restart and Auto-start, enabled by default. Disabling it does not stop a running process; manual Stop is not automatically undone. Only owned processes are managed; an HTTP listener is not adopted.

Confirmed backend upgrades/reinstalls and environment moves preserve the previous running/stopped state, independently of the Auto-start preference. Maintenance refuses active jobs/downloads rather than interrupting a generation. Shutdown gives the owned ComfyUI process time to exit normally before bounded forced cleanup of a hung process; any escalation is logged. The interface refreshes native status after maintenance without remounting and reapplying Auto-start. If DEAS itself was replaced, it waits for maintenance, native work and the project-save guard, then reopens the updated executable. A one-shot resume state restores a previously running backend after that restart without changing the saved Auto-start preference. On Windows the binary is swapped while DEAS runs and DEAS asks **Restart DEAS now?** (Restart now / Later) instead of restarting automatically; see [Application updates](APP-UPDATES.md). Where self-update is unsupported (AppImage, other platforms), **Everything** skips the app step, still updates the backend, and offers **Open releases page**.

Startup optimizations are distinct from per-job Options. Speed+, Compatibility, Off and Custom select validated hardware-qualified launch flags. Speed+ remains the default: it enables Comfy Kitchen INT8 attention and fp16 accumulation on NVIDIA SM 7.5+; older NVIDIA cards, CPU and AMD use ComfyUI defaults. Compatibility and Off add no launch options. Autotune is off in every preset and remains an explicit opt-in in Custom settings; existing saved custom choices are preserved. Review attention/fast features, VRAM/reserve, VAE and advanced precision/cache settings before Apply. Package-dependent choices require their actual packages. Apply can restart the owned backend and is blocked while a job is active; it is not read-only. These presets are not a measured optimization scan.

Backend startup also offers **Disable partner nodes (paid API models)**, checked by default: DEAS recipes never use ComfyUI's paid API node catalogue, while a 2026 core measured on a reporter's machine put those classes at 355 of 1 390 node definitions and 1.3 MB of a 2.8 MB `object_info` response (ByteDance, Kling, Tripo, Gemini and Vidu leading, plus a 239 KB price table). That is the payload every readiness probe, **Backend → Test/Inspect** call and recipe discovery waits for. Unchecking the switch keeps the nodes for workflows you build yourself in the Comfy tab. The choice is orthogonal to Speed+/Compatibility/Off (those only select performance flags), is revalidated at every start, and takes effect on the next backend start. When the installed core predates ComfyUI's `--disable-partner-nodes` flag the switch is greyed out with a named remedy (update the backend under **Backend**) and the argument is never passed, so an old core cannot die on an unknown option. Default ON is an owner decision and an explicit exception to the new-switches-default-OFF rule; the payload share is measured, an actual startup-time saving on a specific machine is not claimed.

`--fast autotune` enables cuDNN convolution benchmarking (`torch.backends.cudnn.benchmark`), not `torch.compile` or CUDA graphs. Studio's separate **Torch Compile** option also defaults off. For interactive work with changing models or resolutions, leave autotune off unless testing shows a benefit; repeated fixed-shape workloads are candidates for manual opt-in. cuDNN benchmarks new convolution size parameters and reuses the selected algorithm for matching parameters within the process: changing mask contents at the same shape does not by itself require another benchmark, though a changed crop size or execution path can introduce new parameters. See [PyTorch's CUDA convolution benchmarking notes](https://docs.pytorch.org/docs/stable/notes/randomness.html#cuda-convolution-benchmarking). No DEAS A/B speed measurement is claimed here.

See [source](../src-tauri/src/startup.rs), [LLM settings](PROMPTING.md#shared-llm-backend) and [verification](VERIFICATION.md).

## Multi-GPU hosts

A host with several visible NVIDIA cards is supported. During planning, DEAS enumerates every visible GPU (`nvidia-smi`); a single-card host uses that card, while a multi-card host selects by default the gate-passing card with the highest compute capability (lowest `nvidia-smi` index on ties) and names it in a plan warning. A set `CUDA_VISIBLE_DEVICES` environment variable narrows the enumeration to that device. If no visible card passes the driver/capability gates, planning recommends CPU with the first named gate error; nothing silently substitutes another card for a planned one.

After an owned NVIDIA environment is installed, **Backend** shows a **GPU** selector whenever the installed card is visible among at least two cards. It lists every visible card with its frame-buffer size (VRAM) and marks the current choice. Switching requires a stopped backend (the selector is disabled while it runs or during any environment maintenance) and refuses targets that need a different PyTorch profile from the installed one — such a mix asks for a new installation plan instead of changing the profile in place. The choice is persisted to both environment manifests (`deas-plan.json` and `deas-install.json`) and re-captured before reuse; every backend start re-resolves the recorded card by UUID among visible GPUs and pins ComfyUI to it, so a removed or disabled planned card fails startup with an explicit message rather than running on another card. The pin is the `CUDA_VISIBLE_DEVICES` environment variable set to the card's UUID; DEAS passes `--cuda-device all` (not a numeric index) because ComfyUI rewrites `CUDA_VISIBLE_DEVICES` to the numeric value of `--cuda-device`, and CUDA enumeration order can differ from `nvidia-smi` order on multi-GPU hosts. The other card stays available for applications outside DEAS.

## Changes and troubleshooting

If ComfyUI starts but DEAS stays on **Starting**, check the **DEAS** source in **Logs**. Look for `operation=readiness` to see when the owned listener appeared, the overall startup budget (120 seconds) and the result. Required local API probes such as `object_info` and `system_stats` can take up to 45 seconds each, within the remaining startup budget. Slow responses and request failures include the endpoint and elapsed time. Export the DEAS and ComfyUI logs together when reporting a startup timeout; a timeout alone is not a reason to reinstall. If `operation=readiness … Owned ComfyUI API responded` is logged but Studio still reports the backend as not ready, look at the `object_info … (slow response)` lines that follow: their `elapsed_ms` should stay roughly constant. Builds before 0.3.4 re-requested the list every 3 seconds on backends slower than that, so each line grew longer until every request timed out ([#39](https://github.com/darksidewalker/DEAS/issues/39)); 0.3.4 keeps one request in flight.

The first-run download of the pinned uv release makes up to three attempts when the connection drops, times out or GitHub answers 429/5xx (2 s and 5 s pauses, each retry logged as `WARN: download attempt …`). A missing asset, an oversized download or a checksum mismatch fails immediately. Follow [first setup](GETTING-STARTED.md#first-setup-inside-deas) for storage/models/consent. Driver and Git remain external prerequisites. Unsupported profiles/options and missing resources block execution. Read [Logs](LOGS.md); never delete existing environments or stop foreign services to clear a blocker. Full repair/resume, staged rollback and broad hardware/Windows acceptance remain incomplete.
