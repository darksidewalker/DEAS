# Installer, backend, folders and language settings

[Documentation index](README.md) · [Plan](PLAN.md)

## Setup path

Setup is one automatic path in the **Backend** tab, which sits in the top tab band with Studio, Library, Prompt Forge, Chat, TVE, Run Plan, Comfy and Logs. Setup remains accessible after installation; Backend's left menu also holds Startup optimizations, LLM backend and Provider authorization. The install review shows the hardware findings, and a sticky **Review & edit installation** panel on the right holds the storage folder, the Director package (checked by default; Forge · RefMods · Continuity · Output are included parts, not separate choices), a dense plan summary with the step chain, collapsed native warnings and the single green **Start install** authorization. Backend, optional packages, the ComfyUI Git ref and an existing-backend address live under Advanced options. The native plan re-prepares automatically after every edit; any edit invalidates the prepared plan, and choices lock during execution. Managed setup defaults to a new `deas-environment` directly beside the running executable, selects a compatible NVIDIA profile or an explained conservative CPU recommendation, and leaves optional packages/extensions off. The native Linux/Windows x86_64 CPU/NVIDIA baseline installs ComfyUI directly (Windows runtime installation is not yet accepted). Full new CPU and NVIDIA installations, framework computation, owned backend start, real API readiness and stop are verified on Linux. AMD/Intel and optional Sage/Radial/Flash/FFmpeg currently block execution explicitly; there is no simulated success.

Shared `NeuralBlob`, `NeuralPath`, `NeuralGraph` and reusable `NeuralIncludedFeatures` components serve both setup and studio features. Historical animated-road settings are not the current setup contract; preserve reduced-motion behavior and avoid continuous repaints. See [primitive ownership and references](NEURAL-PRIMITIVES.md).

## Folder selection and relocation

After successful installation or checked reopening, **Backend → Environment folder** shows the installed DEAS environment’s full path. **Open environment folder** reveals it in the system file manager, even while the backend is stopped. This is the environment root, not the separately configurable models/input/output folders; an uninstalled draft is never shown as an installed environment. Opening it does not start or modify the backend.

**Move environment…** (beside it) moves the whole environment to a new folder inside a chosen parent, keeping the folder name. It requires no running installation, download or Studio job. After confirmation, a running owned backend is stopped gracefully and restarted at the new location; a stopped backend stays stopped. Same drive: one rename. Another drive: a full copy (links kept as links on Linux; on Windows only uv-cache links are dropped, any other link aborts the copy), and the original is removed only after success. DEAS then rewrites every stored absolute path from the old root to the new one: `deas-plan.json`, `deas-install.json`, `deas-settings.json`, `deas-models.yaml`, `venv/pyvenv.cfg`, text scripts in the venv's `bin`/`Scripts`, the Python path in uv's Windows `.exe` launchers, and absolute links into the old root (uv cache). The moved `venv` Python must start from its new prefix and import PyTorch, and the owned-launch identity is captured anew; on failure the rewrite and move are undone. Models, inputs and outputs in your own folders are not touched.

Native folder selection resolves symlink aliases to their real existing directories before planning; installation execution still refuses symlink substitutions. The first installation review offers optional existing models, input and output folders. They remain an in-memory draft until Start install authorizes the immutable plan; no folder settings or data are written by selection alone. After success, those paths are handed directly to Studio; selecting them again in Settings is not required. Studio rescans a changed model root even if an earlier scan is still pending and ignores results/errors from the old root. Choose the models root containing category folders such as `checkpoints`, `diffusion_models` and `loras`, not an individual category folder.

Relocation currently supports Linux; other platforms reject movement without changing files. After installation, the Backend tab separates saving paths from the explicitly selected **Move files & save folders** action. Moving checks all changed trees for conflicting filenames before copying; it never overwrites a destination file. Close other applications using these folders, stop the owned backend and finish downloads first. Copies are verified before settings are switched and originals removed. Errors preserve original data; cleanup warnings identify retained duplicates. Symlinks inside relocated trees and overlapping trees are rejected rather than followed.

## Language plugins

German, English, Turkish, French, Simplified Chinese and Japanese menus/texts live in decentralized module-owned `locales/*.json` files. Data-only manifests under `src/languages/<id>/manifest.json` register bundled UX languages. Switching language preserves IDs and choices; key parity and source-reference checks run in tests. Raw technical logs/errors remain original. See [localization contract](LOCALIZATION.md).

## Native installer coverage

Rust directly implements verified uv bootstrap, managed Python, isolated venv, ComfyUI reference checkout, pinned CPU/NVIDIA Torch selection and required runtime checks. Selected DaSiWa capabilities share one nodepack dependency, fetched only when needed; selecting a capability does not yet implement its studio UI or install model weights. Plans fix hardware and framework identities and require separate confirmation. Targets must be absent, with an existing nonsymlink parent. Fresh installs refuse existing targets. Explicit owned-environment Upgrade/Reinstall is separate: review its plan; reinstall can replace the owned venv and is not rollback.

Successful native provisioning or checked reopening authorizes the owned backend. It auto-starts by default after installation/open and on app restart; disable **Auto-start backend** in **Backend** for explicit manual startup. Manual Stop is not automatically undone. Native manifests and launch files are checked before reuse, and an OS-held environment lock prevents another DEAS instance from starting the same environment. Lifecycle commands verify exact child/listener ownership and real bounded ComfyUI API responses, expose status/logs and stop only the owned process group. They do not adopt arbitrary running listeners or imply generation readiness. Linux local-process/HTTP fixtures and full newly installed CPU/NVIDIA ComfyUI stacks are verified, including an RTX 5090 CUDA computation and owned service launch.

Read [the port ledger](INSTALLER-INTEGRATION.md) and [native IPC details](../src-tauri/README.md) for unsupported options and verification limits. Node requirements explicitly resolve NVIDIA VFX wheels and select backend-specific llama-cpp-python binary wheels, following the reference installer; unavailable wheels fail without a source build or silent CPU fallback. Complete selected nodepack installation, required Director/Continuity registration and owned API lifecycle are verified on the RTX 5090; model generation and every included feature recipe remain separate acceptance work. Full Go-installer parity is unfinished.

## Adopting a foreign installation

Under Advanced options, **Adopt a foreign installation (rebuild its venv)** lets DEAS take over a local ComfyUI folder it does not already manage. The folder must contain `ComfyUI/main.py`; symlinks and traversal are rejected, and a folder DEAS already manages is refused (reopen it from the saved environment instead). The plan warns, and an explicit confirmation dialog gates the start: DEAS deletes and rebuilds the folder's venv and runtime, resets the chosen ComfyUI ref and manages the backend from then on. Models, inputs, outputs and untracked files are kept. Running servers are not adopted; connect them through the backend address instead.

## Backend lifecycle and startup settings

After successful installation/checked reopening, Backend provides Start/Stop/Restart and Auto-start, enabled by default. Disabling it does not stop a running process; manual Stop is not automatically undone. Only owned processes are managed; an HTTP listener is not adopted.

Confirmed backend upgrades/reinstalls and environment moves preserve the previous running/stopped state, independently of the Auto-start preference. Maintenance refuses active jobs/downloads rather than interrupting a generation. Shutdown gives the owned ComfyUI process time to exit normally before bounded forced cleanup of a hung process; any escalation is logged. The interface refreshes native status after maintenance without remounting and reapplying Auto-start. If DEAS itself was replaced, it waits for maintenance, native work and the project-save guard, then reopens the updated executable. A one-shot resume state restores a previously running backend after that restart without changing the saved Auto-start preference. Windows application self-replacement remains unsupported: a newer binary requires manual replacement after quitting; backend maintenance is separate.

Startup optimizations are distinct from per-job Options. Speed+, Compatibility, Off and Custom select validated hardware-qualified launch flags. Review attention/fast features, VRAM/reserve, VAE and advanced precision/cache settings before Apply. Package-dependent choices require their actual packages. Apply can restart the owned backend and is blocked while a job is active; it is not read-only. These presets are not a measured optimization scan. See [source](../src-tauri/src/startup.rs), [LLM settings](PROMPTING.md#shared-llm-backend) and [verification](VERIFICATION.md).

## Changes and troubleshooting

Follow [first setup](GETTING-STARTED.md#first-setup-inside-deas) for storage/models/consent. Driver and Git remain external prerequisites. Unsupported profiles/options and missing resources block execution. Read [Logs](LOGS.md); never delete existing environments or stop foreign services to clear a blocker. Full repair/resume, staged rollback and broad hardware/Windows acceptance remain incomplete.
